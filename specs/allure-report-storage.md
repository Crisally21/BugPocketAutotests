# Техническое задание: публикация Allure-отчётов на отдельном сервере

## 1. Цель

Развернуть Allure Report Storage на существующем Linux-сервере в отдельном Docker-контейнере. Автотесты продолжают проверять удалённый BugPocket. Сначала тесты запускаются вручную на Windows-компьютере, а готовые результаты публикуются на сервер. На следующем этапе запуск и публикация автоматизируются через GitHub Actions.

Отчёт должен открываться по публичной ссылке без входа в учётную запись. Для публикации результатов используется отдельный секретный токен. Контейнер BugPocket и его настройки не изменяются.

## 2. Исходные условия

- Есть Linux-сервер, на котором работает Docker и контейнер BugPocket.
- Тестовый проект использует Java 17, Maven, JUnit 5 и Allure JUnit adapter.
- Результаты тестов уже сохраняются в `target/allure-results`.
- В Maven подключён `allure-maven` 3.0.2, но конфигурация сейчас явно задаёт генератор отчётов версии 2.37.0.
- Пока тесты запускаются локально в Windows и обращаются к уже развёрнутому BugPocket.
- Основная ветка локально называется `master`; перед настройкой публикации название нужно сверить с default branch на GitHub.

Allure Report Storage требует генератор Allure Report 3. Текущие результаты адаптера Allure для JUnit можно использовать с новым генератором, однако совместимость именно текущего Maven-проекта должна быть подтверждена отдельной проверкой до развёртывания сервиса. См. [документацию по переходу на Allure Report 3](https://allurereport.org/docs/v3/migrate/) и [Allure Maven Plugin](https://github.com/allure-framework/allure-maven).

## 3. Состав решения

1. **Allure Report Storage** — отдельный Docker-контейнер на существующем Linux-сервере.
2. **Постоянное хранилище** — Docker volume для данных сервиса. Перезапуск или обновление контейнера не должны удалять опубликованные данные.
3. **Публичный адрес** — веб-страница отчётов без пользовательской авторизации. Предпочтителен HTTPS через уже имеющийся reverse proxy. Адрес/домен и настройка HTTPS уточняются при подготовке сервера.
4. **Токен публикации** — секрет, необходимый клиенту для отправки результатов. Он хранится локально в защищённой переменной окружения, а на этапе CI — в GitHub Secrets. Его нельзя добавлять в репозиторий, Allure-вложения или вывод команд.
5. **Клиент публикации на Windows** — совместимая версия Allure Report 3 и конфигурация проекта, направляющие сформированные результаты на адрес сервиса.
6. **Позднее: GitHub Actions** — workflow запускает Maven-тесты против удалённого BugPocket и публикует результат в тот же сервис.

В официальном варианте Storage отчёты группируются по репозиторию и ветке; сервис использует отдельное хранилище и токен для публикации. Docker-вариант и его параметры описаны в [официальной документации Allure Report Storage](https://allurereport.org/docs/self-hosted-storage/) и [Docker-инструкции проекта](https://github.com/allure-framework/allure-report-storage/blob/main/docs/docker.md).

## 4. Сценарий работы

### Этап 1 — ручной запуск и публикация

1. Пользователь локально запускает тесты Maven-командой из PowerShell. Тесты обращаются к удалённому BugPocket, как и сейчас.
2. JUnit/Allure записывает результаты в `target/allure-results`.
3. Команда публикации отправляет эти результаты в Allure Report Storage с адресом сервиса и токеном из переменной окружения.
4. В выводе команды пользователь получает ссылку на опубликованный отчёт и открывает её в браузере.
5. Публикация выполняется также при падении тестов. Ошибка тестов должна сохранять ненулевой код завершения запуска; ошибка публикации должна отдельно показывать, что отчёт не был отправлен. Для этого команды запуска тестов и публикации должны быть связаны скриптом PowerShell или эквивалентной последовательностью, которая сохраняет оба результата.

### Этап 2 — GitHub Actions

1. Workflow запускает те же Maven-тесты в CI против удалённого BugPocket.
2. Токен публикации берётся из GitHub Secrets; секрет не выводится в лог.
3. Публикация запускается независимо от результата тестов, чтобы в отчёте были видны падения.
4. В workflow передаются репозиторий и фактическая ветка, чтобы отчёты разных веток не перезаписывали друг друга.
5. Политика запуска workflow (вручную, при push или оба варианта) определяется перед началом этого этапа.

## 5. Ветви и срок хранения

- Отчёты каждой ветки должны отображаться отдельно.
- Для каждой ветки сохраняется только самый новый опубликованный отчёт; более старый отчёт этой же ветки удаляется.
- Публикация из одной ветки не должна заменять текущий отчёт другой ветки.
- Необходимо проверить поддерживаемый выбранной версией Storage способ автоматического ограничения числа отчётов до одного. Если такой режим отсутствует или не обеспечивает удаление старой записи, предусмотреть явную очистку старого отчёта через поддерживаемый API сервиса.
- Проверить поведение для основной ветки и feature-ветки, а также повторную публикацию в каждую из них.

Официальная документация Storage описывает хранение опубликованных точек отчётов и API удаления. Поэтому требование «оставлять только последний отчёт» должно быть проверено на выбранной версии сервиса и не должно считаться выполненным только за счёт ограничения отображаемой истории.

## 6. Требования по безопасности и данным

- Веб-страница отчёта общедоступна; любой посетитель, получивший ссылку, может прочитать содержимое.
- Секрет нужен для публикации, а не для просмотра отчёта; токен нельзя размещать в репозитории или передавать в браузерные ссылки.
- Использовать HTTPS для публичного адреса, если доступный reverse proxy и домен это позволяют.
- До включения автоматической публикации убедиться, что вложения Allure не содержат паролей, токенов, персональных данных или иных секретов. Особое внимание — прикрепляемым запросам и ответам API.
- Не менять конфигурацию, контейнер или данные BugPocket в рамках развёртывания Allure Storage.

## 7. План выполнения

1. Проверить совместимость текущих JUnit-результатов и Maven-проекта с Allure Report 3; получить локально открываемый отчёт.
2. Проверить на сервере доступный порт, домен/адрес, существующий reverse proxy и способ выпуска HTTPS-сертификата.
3. Зафиксировать совместимые версии Storage и клиента публикации; подготовить Docker Compose с постоянным volume, перезапуском контейнера и секретами вне файла в репозитории.
4. Развернуть Storage рядом с BugPocket, не меняя его контейнер; проверить перезапуск сервиса и сохранность данных.
5. Настроить ручную публикацию с Windows и разделение по веткам.
6. Проверить замену старого отчёта новым в той же ветке и сохранение отчёта другой ветки.
7. После успешного ручного этапа добавить GitHub Actions, хранение токена в GitHub Secrets и публикацию даже при падении тестов.

## 8. Критерии приёмки

- Allure Report Storage запущен отдельным Docker-контейнером на существующем сервере.
- Данные сервиса сохраняются после перезапуска контейнера.
- BugPocket продолжает работать без изменения своего контейнера и конфигурации.
- С Windows можно запустить тесты против удалённого BugPocket, опубликовать их результаты и открыть отчёт по публичной ссылке.
- Публикация отчёта выполняется и при упавших тестах; первоначальный статус тестового запуска при этом не теряется.
- Отчёты как минимум двух веток разделены; повторная публикация в одной ветке не затрагивает другую.
- После новой публикации в ветке предыдущий отчёт этой ветки удалён, а не просто скрыт из списка.
- Токен не хранится в Git и не раскрывается в логах.
- После отдельного этапа автоматизации GitHub Actions запускает тесты и публикует отчёт с теми же правилами.

## 9. Что ещё нужно установить перед внедрением

- Публичный домен или адрес сервера и доступный порт.
- Есть ли на сервере reverse proxy и HTTPS-сертификат, либо нужно включить Storage за существующим прокси.
- Как называется default branch на GitHub (предположительно `master`, по локальным веткам).
- Какой точный механизм удаления старого отчёта поддерживает выбранная и зафиксированная версия Storage.
- Как запускать GitHub Actions после MVP: вручную, при каждом push или по обоим событиям.

Эти сведения не мешают зафиксировать архитектуру, но понадобятся для готового Docker Compose и пошаговой инструкции развёртывания.
